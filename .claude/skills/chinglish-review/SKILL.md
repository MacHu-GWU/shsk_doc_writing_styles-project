# Review the good versions

**Before anything else, invoke the `chinglish-spec` skill** (or read
`.claude/skills/chinglish-spec/SKILL.md`).

One job: read `tmp/view.md`, decide which `03-good.md` versions are not good enough, and list
them with one sentence each. The output is a worklist the author hands back to
`chinglish-rewrite`.

Nothing else. Do not fix anything, do not touch any case directory, do not rewrite a single
sentence. The only file written is the report.

## Input

A cases folder, in which case the target is its `tmp/view.md`, or a direct path to a `view.md`.
If it does not exist, say so and stop: it is generated by `chinglish-index`, which has to run
first.

`view.md` carries everything needed per case: the folder name, the `context` line, the Chinese,
the bad English, and the good English. The group banner above each run of cases gives the case
type. Read only this file.

## The standard

The checklist is the section titled **"What 'good' has to mean here"** in
`.claude/skills/chinglish-rewrite/SKILL.md`. Read that section, and only that section, at the
start of the run.

It is deliberately not copied here. Two lists drift apart, and a reviewer enforcing a stricter
or looser standard than the writer was given produces findings nobody can act on. The reviewer
holds the writer to exactly the brief the writer had.

## Why this is harder than it looks

This project already rejected LLM scoring of translations, for a reason that applies with full
force here: **cold, formulaic English is the model's own default voice.** Asked "is this good
English?", a model rates the exact prose this pipeline exists to eliminate as excellent. A
review that judges by ear will return a clean bill of health on a folder full of problems.

So do not judge by ear. Check against the checklist, and check against the Chinese sitting
right above it.

Two guards, in both directions:

- **Every finding quotes the offending span** from the good version, and names which rule it
  breaks. No quote and no rule means no finding.
- **Do not manufacture findings.** A batch that genuinely passes should be reported as passing.
  Each false positive costs real rewriting work, and a worklist padded with taste disagreements
  trains the author to ignore the whole report.

## What counts as a finding

Six classes. Tag each finding with one.

| Tag | The good version... |
| :--- | :--- |
| `rule` | breaks a Never or misses an Always from the checklist: a dash in body text, an LLM tell, surviving CJK, every sentence the same length, no contraction anywhere in a fragment that is someone talking |
| `chinglish` | still shows a symptom it was supposed to remove: carried-over clause order, a calque, a literal term where English has its own name, connector overuse, article trouble, redundancy from Chinese emphasis |
| `contrast` | is the bad version with a few words swapped, so the pair demonstrates nothing |
| `content` | says something the Chinese does not, or drops something the Chinese does |
| `form` | changed the shape: bullet count, paragraph count, or diagram graph syntax |
| `register` | does not match its `context` line: the context describes a hands-on tutorial and the English reads like a reference manual, or the reverse |

`contrast`, `content`, `form`, and `register` are only visible because the Chinese, the bad
English, and the context are all on the page. Those are the four a by-ear review misses
entirely, so give them a deliberate pass rather than reading top to bottom once.

A case may earn more than one finding. Report the most actionable one and mention the rest in
the same sentence.

## Execution flow

### Step 1 — Split

Split `view.md` on its `## NNNN-slug` headings into chunks of at most 20 cases. Keep each case
whole. One subagent per chunk, running in parallel.

Each subagent receives its chunk, the checklist section, and the finding classes above. It
returns findings only, in case order, and writes nothing.

### Step 2 — Merge

Collect findings, sort by case number, and write `tmp/review.md` next to `view.md`:

```markdown
# Review: <folder name>

<N> cases reviewed, <M> flagged.

| case | 问题 | 一句话 |
| :--- | :--- | :--- |
| 0007-topic-fronted-list | chinglish | 长定语仍然堆在名词前面, "the you-created repo" 这一处照搬了中文语序 |
| 0012-recap-comma-splice | rule | 正文里有一个 em dash, 应该断成两句 |

## 打回重写

0007-topic-fronted-list
0012-recap-comma-splice
```

The trailing list is plain case folder names, one per line, so it can be pasted straight into
`chinglish-rewrite`. That skill refuses to overwrite a non-empty `03-good.md` unless the cases
are named explicitly, and this is that list.

### Step 3 — Report

1. Cases reviewed, cases flagged, and the count per tag.
2. The table itself, if it is short. If it runs long, give the counts and point at
   `tmp/review.md`.
3. **Any tag that is unusually common**, in one line. Twelve `rule` findings all about dashes
   is one instruction to fix in `chinglish-rewrite`, not twelve rewrites. That observation is
   worth more than the individual findings.
4. If nothing was flagged, say exactly that, and say how many cases were checked so the author
   can judge whether to believe it.

## What this skill must not do

- **Never edit a case.** Not `03-good.md`, not the meta, not `view.md`.
- **Never propose replacement text.** A suggested rewrite in the report becomes the rewrite,
  and it was written without the Chinese in view the way `chinglish-rewrite` has it. One
  sentence on what is wrong, nothing more.
- **Never score anything.** No ratings, no 1-to-5, no ranking of cases or of the folder. Either
  a case has a named defect or it does not.
- **Never flag the bad version.** `02-literal.md` reading badly is its purpose.
