# Chinglish 案例库: 五个 skill 的设计

这份文件说清楚 `chinglish-spec`, `chinglish-collect`, `chinglish-rewrite`, `chinglish-index`, `chinglish-review` 这五个 skill 为什么存在, 以及为什么被切成这个形状. 具体的目录布局, 字段, 执行步骤都写在各自的 SKILL.md 里, 这里不重复.

英文版见 [README.md](README.md).

---

## 1. 要解决的问题

`rewrite-en-*` 那几个 skill 负责把作者的中文技术文档改写成英文. 它们的 SKILL.md 里需要一组 ❌/✅ 对照例子, 用来告诉模型什么叫 Chinglish, 什么叫地道英文.

麻烦在于这组例子不能坐在桌前想出来. 手工枚举会同时踩两个坑:

- **覆盖面等于枚举者当天想到了什么.** 没想到的那一整类问题, 永远不会出现在清单上, 也就永远不会被修.
- **模型会过拟合到清单上.** 给它一份具体坏例子的列表, 它会开始拿句子去比对列表, 而不是根据原文的信息自主判断怎么写更顺. 例子写得越具体, 这个副作用越强.

这两条是矛盾的: 例子太少讲不清楚什么叫 Chinglish, 例子太多又把模型带偏. 平衡点不能靠拍脑袋找.

所以例子必须是**挣来的**, 不是想出来的. 先攒几百个真实案例, 从中归纳出反复出现的 pattern, 再给每个 pattern 挑一两个最有代表性的. 判断标准很硬: **一个在案例库里只出现过一次的案例, 不配进 SKILL.md.** 库是证据, 最后写进 skill 的那十几个例子是结论.

这五个 skill 就是从证据走到结论的那条流水线.

## 2. 数据流

```text
        中文文档, 以及它已有的英文译本
                    |
        chinglish-collect      切成片段, 收 (中文原文, 烂英文) 两件套, 无差别追加
                    |
        chinglish-rewrite      给每个片段补上 "英文母语者本来会怎么写"
                    |
        chinglish-index        看着整堆去重, 修剪, 按 pattern 归类, 出通读版
                    |
        chinglish-review       通读一遍, 挑出哪些 03 其实不够好, 打回上一步
                    |
             一份 pattern 清单
                    |
             写进 rewrite-en-*/SKILL.md

        chinglish-spec  ----  其余四个共同依赖的词汇表和数据契约
```

`rewrite` 和 `review` 之间是个环: review 的产出是一份 case 名单, 直接喂回 rewrite 重写那几个. 环什么时候停由人判断, 不由分数判断.

一个案例是一个**片段**, 不是一整篇文档. 片段要小到读者一眼能同时看见三样东西: 中文那侧是什么构式, 它造成了什么损伤, 正确的写法长什么样. 一整篇文档做不到这一点.

## 3. 为什么切成五个

一句话: **这五件事需要的成本, 判断力, 和视野范围完全不同, 合在一起会得到一个三头不靠的东西.**

**`chinglish-collect` 是体力活, 要便宜, 要不加判断.** 它要扫过上百篇文档, 每篇挖出几个到几十个片段. 这个阶段任何形式的挑剔都是有害的: 它看不见全局, 没资格判断某个案例是不是重复, 也没资格判断类型分布够不够均衡. 它的职责就是无差别地往库里追加.

**`chinglish-rewrite` 是精细写作, 一次只处理一个片段.** 写出 "英文母语者本来会怎么写" 是这条链上最贵也最需要判断力的一步, 和批量扫描是完全不同的操作. 混进采集里, 它会被采集的节奏拖成敷衍.

**`chinglish-index` 需要看见整堆才能工作.** 去重, 修剪, 归纳 pattern, 每一件都要求全局视野. 它是唯一有权删除, 重排, 重编号的 skill.

**`chinglish-review` 必须只读.** 它挑毛病, 不修毛病. 一个既能挑又能改的 agent, 遇到自己挑出来的问题会顺手改掉, 于是没人知道改了什么, 也没人能判断它的判断力值不值得信. 更要紧的是它连替换文本都不许给: 报告里一旦出现建议写法, 那句建议就会变成最终稿, 而它是在没有中文在手的情况下写出来的, 而 `chinglish-rewrite` 是有的.

**`chinglish-spec` 不是任务, 是词汇表.** 其余四个 skill 共享同一套数据契约. 把契约写四遍, 四份就会慢慢走样, 而这种走样只会在几百个案例已经归档之后才暴露出来. 所以契约只写一处, 其余四个开头强制加载它. 它对用户不可见, 因为它不是一个能 "执行" 的动作.

## 4. 三条贯穿全局的设计决定

### 4.1 烂翻译是捡来的, 不是造的

这条管线里**没有任何一步把中文翻成英文**. 中英两侧在采集开始之前就都躺在磁盘上了: 中文是作者的原文, 英文是某个上游流程真实吐出来的译本. 采集只做摘录.

这一点看着像细节, 其实是整个库能不能用的命门. 一旦允许某个 skill 去补上缺失的英文那侧, 库里就开始混入现实中从没被任何管线产出过的文本, 而且**下游分辨不出来**. 更糟的是, 一个手握中文原文, 又知道自己的产物是要当反面教材的生成器, 会写出漫画式的坏英文, 而漫画什么都教不了.

所以中文文档如果配不到英文译本, 它就不是材料: 跳过并报告, 不许补.

同一个道理在项目早期已经付过一次学费. 那时的设计是先翻译出一份忠实但生硬的英文, 再让下游去润色, 实测失败, 原因是**编辑和写作是两种不同的认知操作**: 纸上一旦出现一个合语法的句子, 下游就只会做局部修补, 不会重新生成. 反过来看也一样, 一个瞥见过好版本的直译器不再产出 translationese, 而是产出 "轻度编辑过的好英文", 两侧一旦互相靠拢, 这一对就再没有对照价值.

同理, 烂翻译摘录进来之后就不许再动. 它读着别扭正是它的用途.

### 4.2 平衡是成品的目标, 不是采集的动作

案例分五类, 从单句到连续几段到图表标签. 成品库希望五类大致均衡, 因为它们的失败方式不同, 一个 80% 都是单句的库只教会了问题里最容易的那一小块.

但真实文档供给什么就是什么: 有的文章一张图都没有, 有的通篇是长论述. 让采集阶段去凑比例, 只会凑出一堆勉强算数的弱案例, 而弱案例是负资产.

所以采集阶段照单全收, 只记录类型; 均衡由 `chinglish-index` 在看得见整堆的时候**通过删除过剩的那一类**来达成. 没有任何一步靠补齐来平衡.

### 4.3 采集期追加, 清理期整理

采集不去重, 不排序, 不合并, 不因为某个案例像已有的第 42 号就跳过. 理由有两条: 采集阶段看不见全局, 判断 "重复" 本来就不具备条件; 而清理阶段要看出哪些 pattern 是真的高频, 需要的是未过滤的原貌.

顺带一提, 采集期的编号顺序无所谓, 因为 `chinglish-index` 是按 slug 而不是按编号重排的. 那一步之后, 目录布局只由案例内容决定, 和当初采集的先后无关. 同一批材料重采一遍, 排出来是一样的.

代价是采集期的库看起来很脏. 这是预期之内的. 案例文件属于版本控制 (它们是对照测试的参考材料, 不是临时产物), 但作者的习惯是**过完 `chinglish-index` 再 commit**, 所以采集途中文件夹没进 git 是正常状态.

## 5. 一条容易被忽略的质量红线

**指认不出中文那侧诱因的案例, 一律丢弃.**

只说 "读起来不自然" 没有价值. 一个说不清病根的案例, 教给模型的是 "凭感觉改写", 那恰恰是这条管线要消灭的东西. 用词偏好, 长短句取舍, 段落切分差异, 都不算案例.

同理, 如果某个片段的英文那侧压根还是中文 (图表标签没翻, 列表项漏了), 那是材料本身的窟窿, 不是案例, 直接跳过并计数. 这类窟窿一多, 说明那篇英文根本没翻完, 该先修材料而不是继续挖.

## 6. 当前状态

五个 skill 都能跑了. `chinglish-index` 的重编号, 出索引, 出通读版三件事由一个脚本完成; 去重, 按比例修剪, pattern 归纳还没做, 那一节里留了各自的待决问题.

`chinglish-review` 有一条要提防的东西, 写进它的 SKILL 了: 这个项目早就否决过让 LLM 给译文打分, 理由是**冷冰冰的公式化英文正是模型自己的默认文风**, 让它评自然度, 它会把你正想消灭的那种文字评成优秀. 同一个陷阱对 review 完全适用. 所以它被禁止凭语感判断, 必须逐条对着清单和中文核, 而且**每一条 finding 都要引用出问题的那一小段并指名违反了哪条规则**, 引不出来就不算 finding. 反方向也堵了: 不许为了显得尽责而凑数, 一条假阳性就是一次真实的重写工作量.

原来悬着的那个问题, 重写者该不该看见烂翻译, 已经定了: **看, 但要在自己写完之后才看.** 不看就没法确认这一对是不是真的只隔离了一个构式; 先看就会退化成打补丁, 而补丁会把中文的句子架构原样带过去. 所以 `chinglish-rewrite` 的方法被拆成有先后的五步, 写在前, 比对在后, 而且明确说了不许把这两步合并.

还有一条值得单独记一笔. 好翻译这一侧最终是要被抄进 `rewrite-en-*/SKILL.md` 当 ✅ 范例的, 所以它必须守作者自己那套规范, 尤其是**正文不用破折号** 这一条. 作者一直在用的那份 Claude Project 提示词产出的英文大量使用破折号, 那个习惯如果在几百个 ✅ 范例里被复制一遍, 下游每个 skill 都会学过去.
