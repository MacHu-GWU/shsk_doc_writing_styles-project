# 中文文档的英文重写管线, 设计与决策记录

这份文档记录 `rewrite-in-en-*` 这条管线为什么长成现在这样. 它写给我自己和以后接手的 agent 看, 所以
里面**失败的尝试和最终的设计占同样的篇幅**. 半年后如果有人想把某个被砍掉的东西建回来, 这里应该能
回答 "当初为什么砍".

写作规范用仓库自己那套: 中文叙述, 术语保留英文, 全部英文半角标点.

---

## 1. 我要解决什么问题

平日里我写很多博文, 教程, 技术文档, 设计文档, 调研报告.

因为中文是母语, 我一般先写中文版. 这样能快速成型, 把精力放在观点和内容上, 而不是措辞. 然后再产出
英文版.

这里说的是**重写, 不是翻译**. 观点, 例子, 以及文章结构 (H1/H2/H3 的层级和顺序, 段落, bullet list,
code block, markdown table, quote 的相对位置) 保持不变, 意群保持不变. 在这个骨架之内, 用英文重新
表达.

我曾经有一个 `translate-to-en` 的 skill 干这件事. 产出基本都是翻译腔: 逐句对应, 语法挑不出毛病,
母语者一读就知道味道不对.

后来文章越攒越多, 一个 skill 明显不够用了. 我的文档大致分三类:

- **tutorial** 以 GitHub repo 形式存在的系列教学课程, 通常多篇内容相关, 组成一个系列.
- **explainer** 以公开博客形式存在的博文. 不一定是技术内容, 也可能是个人成长. 有的有教学性质, 有的
  独立成文, 有的若干篇成系列.
- **report** 调研报告, 架构设计, 项目设计, 项目内部 runbook, 开发者和维护者文档.

这三类之所以要分开, 是因为它们的读者和语域真的不同. 至于为什么第二类叫 explainer 而不是 blog, 见
第 6 节.

除了翻译质量差, 还有三个问题:

- **一致性.** 为一个系列而不是单篇写英文版时, 如果用 subagent 并行处理, 上下文不共享, 术语和指代
  就会互相打架.
- **风格无处安放.** 不同类型的文章风格理应不同, 但一个 skill 撑不住这么多变化.
- **无法一步到位.** 经常搞成先 translate 再精修两步走.

## 2. 走了很久的一条弯路: 想用规则解决 chinglish

这一节是这份文档里最重要的一节. 我在这条路上花掉的时间比其他所有事加起来都多, 而它是错的.

**我的假设是: chinglish 是个知识问题.** 模型不知道哪些中文构式会翻出什么样的坏英文, 所以只要把这些
构式一条条写清楚, 它就能避开.

于是我做了一件当时看起来完全合理的事. 从自己已发布的中英对照里挖片段, 每个片段装三个版本 (中文
原文, 烂翻译, 好翻译), 攒了 222 个 case, 从中归纳出十条 pattern, 连同禁用词表, 语域默认值, 动笔前
的自查清单, 一起写进写作者的规范. 那份规范最后有一万两千词.

**这条路失败了. 不是效果一般, 是净负作用: 加进去的每一条规则都让产出更差.**

### 2.1 失败长什么样

一次真实的 20 篇跑动, 20 篇产出的段落数和中文原文**一个不差**. 90 段的文档也是 90 段. 规范里那条
"可以合并, 拆分, 重排" 的授权, 在 900 多个段落里一次都没用过.

后来把管线改成三阶段, 让写作者拿不到中文, 只拿一份逐字草稿. 五篇文档的产出全部是 `草稿 + 3` 段.
不是巧合, 是刚好够绕过我当时设的那条检查.

### 2.2 为什么规则会输

**可验证的目标会挤掉不可验证的目标.**

anchor 计数, 链接改写, 数字守恒, 代码翻译, 禁用词, 全都是可以当场核对的. "读起来像母语者写的" 不
可核对. 一个执行体同时背着两组目标时, 可核对的那组必胜, 因为它能确认自己做到了. 而同时满足全部可核
对约束最省力的走法, 恰好就是逐段对译.

我每加一条规则, 就往可验证那一侧加一份重量.

### 2.3 那次决定性的对照实验

同一篇文档的同一份草稿, 三个版本的写作者:

| | 规范体量 | 中文可见 | 结果 |
| :--- | ---: | :--- | :--- |
| A 完整规范 | 约 12000 词 | 否 | 明显最差 |
| B 薄提示词 | 约 50 行 | 否 | 明显好过 A |
| C 薄提示词 | 约 50 行 | 是 | 明显好过 A |

B 和 C 都明显赢, 而且赢的幅度是人一眼能看出来的.

这同时推翻了我先后持有的两个假设:

- **"规则写得不够细"** 是错的. 加规则的方向本身就是反的.
- **"中文在上下文里造成锚定"** 也是错的. C 组看着中文, 照样赢.

真正的变量是**注意力分配**. 规范越厚, 模型越往 "逐段处理并核对" 那个模式走. 那份赢了的薄提示词, 除
了骨架不变和不许用破折号之外只有一句话: 其他你自由发挥.

### 2.4 唯一活下来的两样东西

**一条理解, 不是一条规则.** 中文是意合的, 逻辑关系留给读者推断; 英文是形合的, 逻辑关系必须写在纸上.

> 中文: 大公司校招, 标准化筛选, 打动 ATS 和 Recruiter
> 烂: Large company campus recruiting. Standardized screening, win over the ATS and Recruiter
> 好: Campus recruiting at large companies **runs through** standardized screening, **so you need
> to** win over the ATS

好的那版做的不是把逗号改成句号, 是**把中文省略掉的两个逻辑关系找出来写进去**. 这条现在留在 core
里供校对阶段参考, **不进写作者的上下文**.

**八段正面样本.** 示范和规则不是一回事. 示范便宜, 模型天然会模仿; 规则贵, 而且挤占生成. 所以风格
现在只用示范表达: 一个 voice block 里放八段目标声音, 加上三四条文体默认值, 一共约 55 行.

### 2.5 顺带被证伪的一个副产品

那 222 个 case 里 81% 是句子级的. 我当时就担心过, 如果规范由这批句对堆成, 模型学到的框架会是 "逐句
翻译, 然后逐句比对这些形状再修一遍", 于是特意规定块级例子要占一半以上, 又特意把规则写成 "动笔前的
决定" 而不是 "修复对照".

**这些防护做了, 而且都没用.** 问题不在例子的粒度, 也不在规则的措辞, 在于规范存在本身.

案例库没有白做. 它的用途换了: 不再是规范的来源, 而是那八段样本的来源, 以及校对阶段的参考.

## 3. 三个阶段

```text
中文  ──(1) drafter──>  逐字草稿  ──(2) rewriter──>  英文成品
  │                                                     ▲
  └─────────────────(3) reconciler ────────────────────┘
```

| 阶段 | 干什么 | 模型 |
| :--- | :--- | :--- |
| drafter | 全部机械活: 事实, 数字, anchor, 代码英文化, 链接改指向, 例子本地化. **明确要求不许写得好听** | sonnet + low |
| rewriter | 只写作. 拿到中文, 草稿, 和约 55 行 voice block. **不加载任何 skill** | opus + high |
| reconciler | 校三条链路, 修机械缺陷, 做全套一致性 | sonnet + medium |

分成三段的理由就是第 2.2 节: **drafter 存在的意义是把全部机械义务吸走, 让 rewriter 一条都不背.**

### 3.1 中间稿的身份

我一度砍掉过中间稿, 理由是: 纸上一旦有了合语法的句子, 下游做的就是局部修复, 不是重新生成. 这个观察
是对的, 但由此推出的 "所以不能有中间稿" 是错的.

区别在框架, 不在中间稿存不存在:

| | 失败的两段式 | 现在 |
| :--- | :--- | :--- |
| 给下游的指令 | "润色这段英文" | "你是 X, 请重新写这份文档" |
| 草稿的身份 | 待改进的文本 | **事实台账** |
| 结果 | 局部修复 | 真的重写 |

而且中间稿带来一个当初没预料到的好处: **意群比对从 "中文 vs 英文" 变成 "英文 vs 英文"**, 同语种比对
便宜得多也准得多, 而草稿按构造是完整的.

### 3.2 保护这个设计的三条规矩

**风格只用示范, 不用规则.** 见 2.4.

**voice block 由编排者逐字复制进任务提示词**, 不让 rewriter 自己去 load. 顺带把静默加载失败那条路
堵死, 见第 9 节.

**缺陷的修法永远不进 rewriter 的提示词.** 当某个缺陷反复出现, 修法属于 drafter 或 reconciler. 往
rewriter 里加东西就是这条管线坏掉的方式. 这句话在 core, 三个 style skill, 和这份文档里各存一份, 因为
它是最容易被下一个人 (包括下一次的我) 好心违反的一条.

## 4. 什么守恒, 什么自由

这条约束的形状来自一个具体需求: **中英两版是并排发布的**. 读者会在两版之间来回切换, 跨文档链接必须
落在正确的语言上.

**守恒的是 anchor**: 标题的层级数量顺序, 代码块, mermaid, 图片, 表格, 引用, bullet 和有序列表, 分隔
线. 类型, 数量, 相对位置不变. 另外外部 URL 逐字节不变, 跨文档链接改指向英文版, 代码里不许有中文,
产出里任何地方不许有 CJK.

**anchor 之间的一切完全自由.** 段落数, 段落顺序, 句子边界, 论述顺序, 全部放开.

**意思守恒**: 每个论点, 指令, 警告, 例子, 数字都要在. 关键区分是**删掉一句冗余的重复表述是必须做的;
删掉作者只说过一次的论点是禁止的.**

### 4.1 段落级的守恒被砍掉了

早期版本的 "骨架" 里含着段落级的预期, 而**段落切分本身就是中文的形状**. 我甚至为此加过一条硬检查:
产出的段落数与草稿完全相同即失败.

两个实测把它否掉了:

- 一次真实跑动里, 五篇文档的成品全部是 `草稿 + 3` 段. 加三个段落就能过检查, 而产出仍然是润色.
- 一份人判定为好的重写, 在同一篇文档上**也是 +3 段**.

**这个指标分不开好坏, 所以它不该装作能分.** 现在段落对应完全放开, rewriter 被明确告知一次写完整篇,
不许顺着草稿一段段走.

## 5. 一致性: 重写在前, 对账在后

### 5.1 两件事没法一次做对

重点是同时重写多篇的场景. 我试过两条路, 都不行:

- **一个持有全局 context 的 session 串行重写.** 后面的文档质量明显衰减, 因为前面所有文档在跟当前
  这篇抢注意力.
- **先统一术语, 再让 subagent 参考对照表并行重写, 就此收工.** 出现各种奇怪问题, 因为对照表只能覆盖
  预料到的部分. 注意这一条失败在 "就此收工", 不在 "前置定死术语", 见 5.3.

结论是: **重写和一致性是两个冲突的目标, 必须放在两个上下文隔离的执行体里.** 顺序不能反, 而且**对账
必须在它自己的 session 里直接改**, 不是只提修改意见再发给别人改的模式.

隔离在这里是**正确性要求, 不是上下文卫生**. 对账者必须看不到写作者的理由, 否则它会接受那些理由.

### 5.2 共享的是简报, 不是全文

但 "每篇只看自己" 也是错的. 没有哪个讲师会在不知道第 1 到 6 课讲了什么的情况下写第 7 课.

而 "把整个系列发给每个写作者" 同样是错的:

| | 每人读全部 | 共享简报 |
| :--- | :--- | :--- |
| 读取次数 | N × N | N + N |
| 注意力 | 写第 7 篇时另外 N-1 篇在抢 context | 只有约束到它的那一页 |

**注意力稀释正是 "长文档后半段质量衰减" 的机制, 放大到整个集合.**

所以有了简报阶段: 读全部草稿, 只产出一页纸, 装各篇的英文定名, 跨篇复现的术语, 本地化替换, 每篇一句
话摘要和阅读顺序, 以及作者声音的特点. 集合大就分片产出局部简报再合并.

简报从**草稿**而不是中文原文提炼. 它的活是定英文标题和英文术语, 在英文里做这个决定更自然, 而且这一
阶段从此不用同时端着两种语言.

简报写到 `tmp/`, **然后继续跑, 不停下来等批准**. 它落盘是为了让我能改完重跑写作阶段, 不是一道闸门.

**简报必须按 markdown 规范写, 包括不许用破折号.** 它是每个写作者动笔前读到的最后一段指令文本, 而
模型会模仿指令的语域. 一次真实跑动里, 简报的破折号密度是全场最高的 13.5/千词, 而它污染了下游全部
20 篇. 见 11.2.

### 5.3 术语前置是质量决定, 不是效率决定

我一度把术语一致性全部推给对账阶段事后统一. 这条改了.

理由是**句子是围绕着词造出来的**. 一个用了 `chain` 的写作者会写 "the chain of six stages", 对账阶段
查找替换之后变成 "the pipeline of six stages", 读起来很别扭. 而一个从一开始就知道该用 `pipeline` 的
写作者写的是 "a six-stage pipeline". 后者才是母语者的写法.

所以简报把常用术语前置定死, 对账抓残余. 两道都要.

### 5.4 glossary 的降级史

这个东西差点变成一个静默的错误源, 值得记一下.

最早它是两个隔离阶段之间的交接物. 交接的两端后来都没了, 但引用还在, 三个地方都在引用一个已经没有任何
一步会产出的文件.

修的时候我先把产出方挪到了对账阶段. 后来发现增量场景 (往已发布的 1 到 5 篇里加第 6 篇) 用它是**有害
的**: 这个系列实际说了什么, 真相是**已发布的那几个英文文件本身**, 不是上一轮的 glossary. 两者会分叉,
而**过期的 glossary 不会报错**, 它只会安静地把一个系列早就抛弃的决定传染给新文档.

所以最终它被降级成**可选的人工覆盖入口和审计记录**, 不是管线依赖.

## 6. 三个文体的划分

草稿里第二类原本叫 `blog`, 定稿改成了 `explainer`. 因为那个博客不是个人风格明显的博客, 而是**有商业
品牌, 不与个人绑定的科普和教学输出**. 英文媒体里这种文体就叫 explainer, 而且这个词本身就在给模型下
正确的指令; `blog` 只说了载体, 什么都没说.

三个名字的轴是一致的, **都是文体**:

| Skill | 文体 | 读者的处境 | 主要失败模式 |
| :--- | :--- | :--- | :--- |
| `rewrite-in-en-tutorial` | 手把手教学 | 边读边做, 有活要干 | 步骤指令变成描述句 |
| `rewrite-in-en-explainer` | 品牌科普 | **随时可以走** | 叙事铺垫被压平; 反问被改成陈述 |
| `rewrite-in-en-report` | 正式工作文档 | 带着问题来, 拿到答案就走 | 商业术语被直译; 结构化程度被稀释 |

"读者的处境" 这一列是三个 voice block 里最有用的一句话, 因为其余的取舍都从它推出来.

`report` 同时覆盖分析型 (调研报告, 架构设计) 和操作型 (runbook, 开发者文档). 它们的语域一样, 只在
一条 genre default 上冲突: 省略主语补什么. 解法是一条规则同时覆盖: **补文档所讲的那个东西, 不补
`you`; `you` 只出现在读者确实被要求做事的地方.** 一份文档内部可以合法切换, 切换跟着段落是分析性的
还是操作性的走.

将来如果要加个人风格的博客, 按同一条轴命名 `rewrite-in-en-personal-essay`.

## 7. 用户入口: 一条命令

```text
/doc-writing-styles:rewrite-in-en-tutorial
把这个系列教程以及索引和概览统一作为上下文, 为这些文件创建对应的英文版:
proj/parts/*/*-cn.md
proj/*-cn.md
已有的英文版质量较差, 无需留档, 直接覆盖掉.
```

**这是整条管线, 不是第一阶段.** 它解析, 起草, 写作, 然后自己跑对账, 最后才报告.

### 7.1 阶段 0 的产出是映射表

唯一产出是一张显式的表, 后面每个阶段都只认这张表:

```text
/path/to/a1-cn.md  ->  tmp/drafts/a1.draft.md  ->  /path/to/a1.md   (覆盖已有)
```

目标按优先级推断: 用户显式给的, 这个文档集已经在用的约定, 都推不出来时用不会误覆盖的后缀名.

**把表打出来, 然后继续跑. 推断成功了就不需要许可.** 只在真拿不准时问. **"会覆盖文件" 本身不构成
提问的理由**, 替换掉质量差的旧英文通常就是这次任务的全部目的, 版本控制是兜底.

**用户在同一条消息里说的其他要求也是有约束力的, 而且必须跟着跑.** 一次真实跑动里我要求 "沿用
markdown-style 规范", 而当时的规范明写着只给写作者三样东西 (源路径, 目标路径, 简报), 于是这句话到
编排者就断了. 停在编排者手里的指令, 就是用户眼睁睁看着你无视掉的指令.

### 7.2 编排与磁盘布局无关

目录名, 嵌套深度, 文件名约定, 哪个文件扮演什么角色, 这些都是碰巧拿到的那个仓库的属性. 所以**关系从
文档自身发现**: 它包含的链接, 它声明的标题, 它重复的术语. 绝不从预期的路径模式推断.

比如 "索引" 的定义是行为性的: **一个正文基本都是指向集合内其他文档的链接的文档**, 而不是 "名字叫
README 的文件".

## 8. 确定性检查: 三条链路

```text
中文 ──①──> 草稿 ──②──> 成品
  └──────────③──────────┘
```

一个零依赖的纯标准库脚本, 没有模型在回路里, 零方差, 毫秒级. 有两条规则在不同链路上**语义相反**, 所以
不可能用一套规则跑一条链路了事:

| 规则 | cn-draft | draft-final | cn-final |
| :--- | :--- | :--- | :--- |
| H8 段落 | 漂移超过 25% 即失败 | 只报信息 | 只报信息 |
| H3 链接 | 查有没有**改**成英文 | 查有没有被**改回**中文 | 查是不是英文 |
| H9 数字 | 比出现次数 | 比不同数值 | 比不同数值 |

H3 那一条是实测出来的: 一次纯风格的重写把三个跨文档链接退回了 `-cn`. 只跑 cn-final 能看见失败, 但看
不出是谁弄坏的. **跑全部三条的价值是定位责任**, 在 20 篇的跑动里这决定你重跑的是便宜的那一步还是贵
的那一步.

其余的硬检查: H1 标题骨架, H2 外部 URL, H4 anchor 守恒, H5 代码里无中文, H6 正文无 CJK, H7 破折号,
H9 数字守恒. H10 (分节长度比) 只在第一跳跑, 永不失败, 用途是把语义比对**瞄准**到具体的几个标题区段,
而不是通读两遍两种语言.

**能机器查的就不要交给模型.** 模型层只做机器做不了的事: 意群对账和跨文档一致性.

### 8.1 H9 的分寸是调出来的

第一版拿多重集比数字, 结果报了一个 `120` 缺失. 查下去发现中文里 `120` 出现 7 次英文 6 次, 少掉的是
"也就是 120 个核心小时" 这句给中文读者的注解, 那是**正确的冗余删除**.

所以现在草稿那一跳比出现次数 (转写不许漏), 之后比不同数值 (整个数字消失才算丢).

## 9. skill 还是 subagent, 以及加载必须会响

**判据只有一条: 你需要看见并干预中间过程, 还是只要最终结果?** 需要看见用 skill, 它在主线程里展开;
中间步骤是你永远不会回头看的噪音就用 subagent.

按这条判据, 编排 (阶段 0 和简报) 在主线程, 起草, 写作, 对账都是 subagent.

### 9.1 一个让我损失最惨的静默失败

subagent 的 frontmatter 有个 `skills:` 字段, 号称能在启动时把整份 skill 内容注入进去. 我用了它, 理由
是不用它的话就只能把路径丢给 subagent 指望它自己去读, 而**漏读是静默的**.

诊断对, 解法错. **`skills:` 找不到技能时同样是静默跳过**, 官方文档原话是 "Claude Code skips it and
logs a warning to the debug log".

实际发生的是: agent 里写的是带插件命名空间的技能名, 机器上装的插件是旧版本, 里面根本没有这个 skill,
本地迭代的新版本从未发布. **20 个写作者全部空手上阵**, 而它们的 system prompt 第一句话是 "引擎已经
预加载在你的上下文里了". 四个小时二十多次迭代, 改的全是一份从未被读取的文件.

所以这个解法把 "可能漏读" 换成了 "必定漏读, 而且连 agent 自己都不知道".

**现在的做法**:

- rewriter 什么都不加载, voice block 由编排者复制进提示词.
- drafter 和 reconciler 用 Skill 工具加载, 因为**调用失败是可见的工具报错**, 不是静默跳过.
- 两者都必须在上下文里找到一行 canary 标记, 找不到就立刻停手报 `INSTRUCTIONS NOT LOADED`, 一个字
  都不写.

### 9.2 小而弱耦合宁可重复

一度有一个被多个 skill 引用的共享契约文件. 删掉了, 因为一次审计发现**这个共享是坏的**: 重写 skill
对契约里规则的引用数是 0, 它只是链过去说 "去读这个", 而契约里最需要被重写阶段用到的那部分, 在重写
skill 里出现 0 次. **最需要那份内容的 skill, 离它最远.**

真正的原则是: **小而弱耦合的东西宁可重复, 大而本质耦合的东西必须共用.**

## 10. 语料

```text
evals/
├── rewrite-en-tutorial/
│   ├── pairs/          整篇对照
│   ├── corpus/         只有中文, 冒烟测试用
│   └── chinglish/      片段对照, 222 个 case
├── rewrite-en-explainer/
└── rewrite-en-report/
```

目录名沿用了旧的, 没改, 因为 `chinglish-*` 那几个 skill 引用着这些路径.

**一个必须记住的更正: `pairs/` 的英文侧不是 gold.** 我一度以为它是 "中文原文加我认可的英文版", 实际
上每个 `pairs/*/tmp/source-en-draft.md` 都是旧 `translate-to-en` 管线的产出:

| | 破折号 / 千词 | 残留中文的文件数 |
| :--- | ---: | :--- |
| explainer 8 对 | 6.8 到 14.3 | 8 对里 5 对 |
| report 3 对 | 6.1 到 15.3 | 3 对里 2 对 |
| tutorial 9 对 | 0 到 15.9 | 9 对里 4 对 |

残留中文全在 mermaid 节点标签里, 在现在的管线里是 H5 硬失败. **英文侧是反面教材.** 拿它去归纳目标
声音等于把管线瞄准它要消灭的东西.

真正的正面语料只有 `chinglish/*/03-good.md`, 而且只有 tutorial 有. explainer 和 report 的八段样本是
从中文原文反推着写出来的候选, **尚未人工确认**. 这个状态记在各自的 `CHANGELOG.md` 里, **不写进
`SKILL.md`**, 因为 `SKILL.md` 会进 rewriter 的上下文, 而一份对自己的权威性打折扣的规范会被降权.

## 11. 实测暴露过的问题

纸面上想不到, 只有真跑才会出现的.

### 11.1 第三阶段变成了交棒

一次跑动写完 18 个文件之后停下来, **打印了一条斜杠命令让我去发**, 然后等着.

根因是我的写法: 斜杠语法出现在代码块里, 读作 "给用户抄的东西", 而后面那句 "起 subagent" 位置在下面,
被压过去了.

修法是把代码块整个删掉, 换成机制本身, 再加上反面形式: 不要打印命令让用户复制, 不要问要不要继续, 不
要停下来等. **一份写着 "接下来请跑对账" 的报告, 就是一份没干完的活的报告.**

### 11.2 指令文本在用示范教错的东西

一次产出里破折号明显偏多. 我最初以为该由调用时的 prompt 控制, 量了一下发现不是:

| 文本 | 破折号 / 千词 |
| :--- | ---: |
| 写作者的规范 | 9.8 |
| 模式目录 | 12.6 |
| 对账 agent | 9.3 |
| **它让模型模仿的 220 段声音样本** | **0.0** |

**破折号不是从中文原文来的, 是从我的指令文本来的.** 模型模仿指令的语域.

这条教训后来又复发了一次, 在一个我没覆盖到的位置: **运行时生成的简报**. 静态文件都扫干净之后, 某次
跑动的简报是 13.5/千词, 全场最高, 而每个写作者都读它.

所以规矩是: **凡是会进入下游上下文的文本, 不管是静态规范还是运行时产物, 都受同一套规范约束.**

### 11.3 语域在文档内部漂移

一篇 2100 词的产出, 前三分之一到后三分之一:

| | 前 1/3 | 后 1/3 |
| :--- | ---: | ---: |
| 缩写密度 | 47.7/千词 | 26.5/千词 |
| 平均句长 | 11.8 词 | 16.2 词 |

**开头是写出来的, 结尾是翻译出来的.** 我挑出来的反面例子几乎全部来自后半段.

有一条关联当时没想到: **八段声音样本全部来自文章开头.** 模型对 "中段和结尾该是什么声音" 没有目标,
而漂移的位置和样本缺失的位置完全重合. 补中后段的样本是下一个该做的事, 而且它是**加示范**不是**加
规则**, 符合第 3.2 节的规矩.

### 11.4 检查报了错, 东西照样发了

一次跑动里, 成品带着四个没翻译的中文标签发了出去, 而那正是对账阶段明确要自己修的一类. 同一次里
drafter 编造了新的 blog_id, rewriter 又改了回去, 两个错互相抵消, 所以最终链路看不出来.

**编排者在信 agent 的自述, 没有自己验证脚本的退出码.** 还没修.

## 12. 测量装置失败了两次

第一次是一整套 benchmark: 50 篇语料, 分 dev 和 holdout, 一份 rubric, LLM 评委打分, 方差分解,
hand_edit_rate 作北极星指标, 跨版本 leaderboard. 砍掉的理由是 **LLM 评委在这件事上不可靠**: 冷冰冰
的公式化英文正是语言模型自己的默认文风, 让它给自然度打分, 它会把你正想消灭的那种文字打成高分.

第二次我换了装置, 用零依赖的正则脚本, 零方差, 毫秒级. **它同样失败了.**

同一篇文档, 管线产出对一份人判定为明显更好的重写:

| 指标 | 管线 | 更好的那份 |
| :--- | ---: | ---: |
| 结构检查 | PASS | PASS |
| 词数 | 1917 | 1868 |
| 平均句长 | 13.6w | 13.7w |
| 句长离散度 | 9.5 | 9.4 |
| 缩写密度 | 27.6/千词 | 28.9/千词 |
| 破折号 | 0 | 0 |
| 禁用词 | 0 | 0 |

**两份文档在全部仪表上是同一份文档**, 而人一眼分得出. 差别在四个地方, 一个都不在指标上: 段落节拍
(单句成段是一个节拍), 动词的地道程度 (`fixed` 对 `solved`), 抽象还是具体 (`a pile of unrelated
tricks` 对 `may not look like they add up to much`), 以及比喻直译 (`主线` 译成 `line` 而不是
`thread`).

所以这条教训的最终形态是: **机械层面值得工程化, 风格层面不值得.**

机械层面确实抓到了东西: 成品里没翻译的中文标签, drafter 编造 blog_id 之后 rewriter 又改回来这种两个
错互相抵消的情况. 这些肉眼发现不了, 修法是确定的. 这一层留着.

风格层面, 我写的每一条规则净效果都是让产出更差, 而衡量它们的装置又看不见真正的差别. **不要再建了,
换什么评委都不要.**

## 14. 已知局限和下一步

**explainer 和 report 的八段样本未经人工确认.** 这是整条管线唯一没有人工背书的关键输入. 验证方式是
拿 `evals/` 里的 pair 跑一次, 读产出, 把任何 "不是我会写的" 换掉.

**八段样本全部来自文章开头**, 而漂移发生在后半. 见 11.3.

**core 里那份模式目录现在只有 drafter 和 reconciler 读得到**, 占 120 行. 按第 2 节的结论它对它们大概
也没什么用. 等下一轮实测结果出来, 如果好, 那一节大概也该砍.

**编排者仍然采信 agent 的自述**, 应该自己跑脚本验退出码. 见 11.4.

**report 的语料最薄**, 三对, 其中一对是 50 条 SQL 的参考手册, 结构上和另外两对完全不同.

**长文档的漂移只有部分缓解.** 一万两千字以上的单篇还没有系统验证过.

## 15. 不要做的事

写在这里免得以后又建回来.

- **不要往写作者的提示词里加规则.** 见第 2 节. 这是这条管线已知的坏掉方式, 而且它看起来永远像是一个
  好主意.
- **不要建打分系统, 不要写 rubric, 不要让 LLM 给译文打分, 不要排 leaderboard, 也不要用正则脚本给
  风格打分.** 见第 12 节. 已经失败两次, 换评委没用.
- **不要用 `skills:` frontmatter 给关键路径注入规范.** 见 9.1. 它静默失败.
- **不要为段落对应建检查.** 见 4.1. 这个指标分不开好坏.
- 不要把管线生成的英文提交进仓库. `chinglish/` 下的案例是唯一例外, 那是策划出来的对照材料.
- 不要拿 gold 当唯一正确答案. 它是参照不是判据.
- 不要为了做语料专门写文章. 分布会失真, 而且会不自觉地写得好翻译.
- 不要把三个文体的语料混着归纳. tutorial 的规律套到 report 上大概率是错的.
