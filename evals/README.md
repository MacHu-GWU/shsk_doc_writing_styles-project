# 中译英管线的语料库

这里放的是中译英重写管线的语料. 它不是一套 benchmark, 用途和 benchmark 也不一样, 第 1 节说清楚这件事, 因为搞错方向会浪费很多时间.

目录名沿用了管线早期的命名, 没跟着改, 因为 `chinglish-*` 那几个 skill 引用着这些路径.

写作规范用仓库自己那套: 中文叙述, 术语保留英文, 全部英文半角标点.

---

## 1. 这些语料是干什么用的

**用来逆向推导出风格规格, 不是用来给管线打分.**

原本的设计是攒五十篇语料, 写一份 rubric, 让 LLM 当评委打分, 跑方差分析, 排 leaderboard. 那套东西被砍掉了, 因为它是 "为了精确测量一个我们不知道怎么修的问题" 而建的. 修法已经清楚了, 再建一套比修法本身还贵的测量装置就是本末倒置.

而且 LLM 评委在这件事上本来就不可靠: 冷冰冰的公式化英文正是语言模型自己的默认文风, 让它给自然度打分, 它会把你正想消灭的那种文字打成高分.

**这一节原本还有一段, 说语料的用途是 diff 出模式再把模式写成 skill 里的规则. 那段删掉了, 因为
那条路后来被实测否掉了.**

写进写作者规范的每一条规则, 净效果都是让产出更差. 机制是注意力分配: 规则是可核对的, "读起来像母语
者写的" 不可核对, 而一个执行体同时背着两组目标时可核对的那组必胜. 一次三方对照里, 一份约五十行的
薄提示词明显赢过一份一万两千词的厚规范. 完整的记录见
[cn-to-en-rewrite-design.md](../.claude/skills/doc-writing-styles/docs/cn-to-en-rewrite-design.md)
第 2 节.

所以语料现在只有两个用途, 都不是产出规则:

- **`chinglish/*/03-good.md` 是声音样本的来源.** 风格只用示范表达, 不用规则. 每个 style skill 的
  voice block 里放八段, 就是从这里挑的.
- **`pairs/` 是冒烟测试和人工判断的材料.** 跑一遍, 自己读, 判断好不好.

还有一个必须记住的更正. **`pairs/` 的英文侧不是 gold.** 每个 `pairs/*/tmp/source-en-draft.md` 都是
早期 `translate-to-en` 的产出, 破折号密度 6 到 16 每千词, 大部分文件的 mermaid 标签里还留着没翻译的
中文. 它是反面教材, 拿它去归纳目标声音等于把管线瞄准它要消灭的东西.

至于 "这次跑有没有把文档改坏", 那件事由对账阶段在每次真实使用时自动回答, 不需要语料库.

## 2. 目录结构

一个风格一个目录, 因为三种文体的失败模式完全不同, 混在一起归纳不出规则.

```text
evals/
├── README.md                    本文件
├── rewrite-en-tutorial/         课程材料: 索引型 README, 教程正文
│   ├── pairs/001-<slug>/
│   │   ├── source.md            中文原文
│   │   ├── gold.md              你认可的英文版
│   │   └── notes.md             可选, 但价值最高
│   ├── corpus/                  只有中文, 冒烟测试用
│   └── chinglish/               Chinglish 案例库, 见第 3 节
│       ├── INDEX.md
│       ├── 0001-<slug>/
│       │   ├── 00-meta.toml
│       │   ├── 01-source.md     中文片段
│       │   ├── 02-literal.md    同一片段的烂英文
│       │   └── 03-good.md       同一片段该有的写法
│       └── tmp/view.md          三版并排的通读版, 不进 git
├── rewrite-en-report/           项目设计文档, 调研报告, 参考手册
│   ├── pairs/
│   ├── corpus/
│   └── chinglish/
└── rewrite-en-explainer/        品牌科普博文
    ├── pairs/
    ├── corpus/
    └── chinglish/
```

`evals/.gitignore` 挡住了 `*-en.md`, `*-en-draft.md`, `*-glossary.md` 和 `tmp/`. **管线顺手生成的东西不进仓库**, 进仓库的是原文, 你亲手认可的 gold, 以及 `chinglish/` 下的案例 (那是策划出来的对照材料, 不是管线的副产品, 理由见第 3 节).

`notes.md` 记的是 "你在机器产出的基础上改了什么, 为什么改". 这份东西比 gold 本身更值钱, 因为 gold 只给出结果, notes 给出规则.

## 3. `chinglish/` 是什么

`pairs/` 是**整篇**对照, 用来看一条管线整体跑得怎么样. `chinglish/` 是**片段**对照, 用来回答一个更小也更硬的问题: 中文的哪个构式, 会让英文烂成什么样, 以及该怎么写.

一个 case 是一个目录, 装同一个片段的三个版本: 中文原文, 某次真实产出的烂英文, 以及它本该有的写法. 片段可以是一句话, 一段话, 连续两到四段, 一个 bullet list, 或者一个 mermaid 图. 关键是它必须小到**一眼能同时看见构式, 损伤, 和修法**, 整篇文档做不到这一点.

用途和 `pairs/` 一样, 是逆向推导规格, 不是打分. 攒够几百个 case 之后从里面归纳出反复出现的 pattern, 每个 pattern 挑一两个代表, 写进对应的 `rewrite-en-<style>/SKILL.md` 当 ❌/✅ 范例. 判据很硬: **一个只出现过一次的 case, 不配进 SKILL.md.**

这也是为什么它进 git 而 `pairs/tmp/` 不进. 这些文件是策划出来的对照测试材料, 不是管线的临时产物.

五个 skill 负责这条链, 设计和动机写在 `.claude/skills/chinglish-spec/README-cn.md`:

| Skill | 干什么 |
| :--- | :--- |
| `chinglish-spec` | 共享契约: case 长什么样, 五种类型, 目录和字段格式. 不直接跑 |
| `chinglish-collect` | 从 (中文, 英文) 文档对里挖片段, 写 `01` 和 `02`. 不产生任何英文, 两侧都是摘录 |
| `chinglish-rewrite` | 批量写 `03`, 也就是那句本该有的写法 |
| `chinglish-index` | 重编号, 出 `INDEX.md`, 出 `tmp/view.md`. 提交前跑 |
| `chinglish-review` | 通读 `tmp/view.md`, 挑出哪些 `03` 其实不够好, 一句话说明, 打回重写 |

一个 style 一个 `chinglish/` 目录, 理由和 `pairs/` 一样: tutorial 的规律套到 report 上大概率是错的.

## 4. 三个风格分别在测什么

三个目录不是同一批文章的三种切法, 是三种**真实存在的不同文体**, 各有各的失败模式.

| 目录 | 文体 | 主要失败模式 |
| :--- | :--- | :--- |
| `rewrite-en-tutorial` | 手把手教学, 读者边读边做 | 步骤指令变成描述句; 索引型 README 的枚举照搬中文逗号串 |
| `rewrite-en-report` | 正式文档, 给同事和决策者看 | 商业术语被直译; 全角标点原文的格式残留; 参考手册的结构化程度被稀释 |
| `rewrite-en-explainer` | 品牌科普, 给感兴趣的专业读者看 | 叙事铺垫被压平; 反问被改成陈述; 作者的节奏感丢失 |

每个目录 8 到 10 对 gold 就够. 配比按**压力特性**分, 不按体裁均分, 因为目的是覆盖失败模式而不是取得统计代表性: 重代码块的, 重表格的, 长论述段的, 口语标记密集的, 各来一两篇.

篇幅不限, 而且**长短都要有**. 短文暴露不了寄存器漂移, 长文暴露不了别的. 现有语料从 2KB 到 98KB 都有, 这个跨度是对的.

## 5. gold 怎么做

流程是: 先跑一遍管线拿到机器产出, 然后你**单独开一个 session** 去微调它, 直到你自己认可.

关于锚定, 有一条要留神. gold 由管线自己产出再由你微调, 你会不自觉地接受它给的框架. 判断 "这句要不要改" 的时候, 标准是**"我自己写会不会这么写"**, 而不是 "这句有没有明显错误". 后一个标准会让你放过大量读着别扭但挑不出毛病的句子, 而那些句子恰恰是这条管线要解决的问题.

改完之后把 `notes.md` 写了, 哪怕只有三五行. 每一条 "我把 X 改成了 Y, 因为 Z", 都是下一版风格规格的候选条款.

## 6. 一个 pair 怎么变成 skill 的改进

1. 跑 `/rewrite-in-en-<style> pairs/00N-slug/source.md`, 拿到产出.
2. 自己读. 判断标准是**"我自己写会不会这么写"**, 不是 "这句有没有明显错误".
3. 判断问题属于哪一类, 这一步决定修法去哪:
   - **读起来不像母语者写的** -> 改 voice block 里的**样本**, 不要加规则. 见第 7 节.
   - **意思丢了或者多了** -> 改 drafter 或对账阶段.
   - **结构, 链接, 数字, 残留中文** -> 改确定性脚本或对账阶段.
4. bump 对应 skill 的 VERSION 和 CHANGELOG, 重跑, 自己再读一遍.

第 3 步是关键, 而且它的默认答案和直觉相反. **看到一处不地道的表达, 正确的反应不是写一条规则去禁止
它, 而是问 voice block 里缺了哪一类示范.**

---

## 7. 不要做的事

- **不要往写作者的提示词里加规则.** 这是这条管线已知的坏掉方式, 而且它看起来永远像是一个好主意. 第
  1 节说了为什么.
- **不要建打分系统.** 不要写 rubric, 不要让 LLM 给译文打 1 到 5 分, 不要排 leaderboard, 也不要用正则
  脚本给风格打分. 这件事已经失败过两次, 换评委没用.
- **不要把管线生成的英文提交进仓库.** `.gitignore` 挡住了常见命名, 但你手工重命名过的文件它挡不住. `chinglish/` 下的案例是唯一的例外, 理由见第 3 节; 那个例外不适用于 `chinglish/*/tmp/`.
- **不要拿 gold 当唯一正确答案.** 它是参照, 不是判据. 一个和 gold 不同但同样好的写法不该被算作错误.
- **不要为了做语料专门写文章.** 用你已经写过的真实文章. 专门写的文章分布会失真, 而且会不自觉地写得好翻译.
- **不要把三个目录的语料混着归纳.** tutorial 的规律套到 report 上大概率是错的.
